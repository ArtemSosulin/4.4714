# ЛР3. Категория магазина и канал оплаты

Вариант: **Merchant**.

## Что дано

Предметные объекты, внешний API и вспомогательные типы уже подготовлены. В `app/domain/acceptance.py` даны заготовки общего интерфейса и двух исполнителей. Их поведение и основной метод `MerchantService.check()` требуется завершить самостоятельно. Сигнатуры сохранены; новые слои и выбор архитектуры не нужны.

## Задание

### Шаг 1. Реализуйте общий интерфейс и два поведения

Реализуйте `MerchantAcceptanceRule`, `RestrictedCategoryRule` и `AcceptedChannelRule`.

Первое правило запрещает категорию из заданного множества и возвращает `MERCHANT_CATEGORY_DENIED`. Второе разрешает канал только из заданного множества; иначе возвращает `MERCHANT_CHANNEL_DENIED`.

Пустой набор запрещённых категорий разрешает все категории. Пустой набор разрешённых каналов запрещает все каналы. Сервис вызывает общий `check()`, не меняя данные магазина.

### Шаг 2. Соберите путь вызова в `MerchantService.check()`

Получите магазин и проверьте `availability()`. Затем вызывайте правила по порядку до первого отказа. Пустой набор правил не отменяет статус магазина. Не выбирайте алгоритм по конкретному классу исполнителя.

### Шаг 3. Проверьте повторное использование

Доступный магазин → приостановка и `MERCHANT_SUSPENDED` → активация и разрешение. Отказ не должен запоминаться сервисом.

## Примеры и границы

- При запрете `{GAMBLING}` эта категория отклоняется, `RESTAURANT` проходит.
- При каналах `{POS}` операция `ONLINE` отклоняется.
- Пустые множества обрабатываются по правилам выше.
- Статус проверяется первым; из нескольких отказов правил возвращается первый по порядку.

Последовательности и конфигурации дополнительно проверяются в `tests/test_progression.py`. Прочитайте ожидаемый результат каждого сценария до реализации.

Все проверки открыты: `tests/test_contract.py` и `tests/test_review_contract.py`.
Описание объектов — в [REFERENCE.md](REFERENCE.md), исходные результаты тестов — в [STARTER-STATE.md](STARTER-STATE.md).
